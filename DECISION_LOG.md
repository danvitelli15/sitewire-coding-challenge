# Decision Log

An append-only trace of conscious design/structure decisions made while working on this assessment, in the order they were made.

- Structured the repo as a pnpm workspace so the dashboard, a future core data-handling package, and a future CLI can share code and a single dependency graph.
- Started with a deliberately naive data-loading baseline (plain `fetch` calls fired from a mount `useEffect` in `App.tsx`, no error handling or retries) to prove the API wiring end to end before tackling failures, latency, and the per-user login fan-out.
- Extracted the API fetch functions and types into a framework-agnostic `sitewire-interview-core` package, so the same data logic can back both the dashboard and a future CLI.
- `sitewire-interview-core` ships raw TypeScript source (`exports` points at `src/index.ts`) with no build step; Vite compiles it for the dashboard, and Node's native type stripping can run it directly for the CLI.
- Rendered users as grid-aligned list rows (`UserCard`) rather than a full data table, keeping a lightweight layout that can grow columns for login time and IP.
- Prefer native semantic HTML elements over ARIA roles on generic elements (e.g. real list/table markup instead of `<div role="listitem">`).
- Rendered users as a `<table>` since each row is the same set of columns; row selection will drive a stateful side panel showing all of a user's logins (chosen over rows that expand inline).
- Routed all API requests through a single `apiFetch` wrapper in core, creating one bottleneck where failure handling, retries, and timeouts will live instead of being repeated in each endpoint function.
- `apiFetch` retries 500 responses with backoff (`0, 500ms, 1s, 2s, 4s` before each of up to 5 attempts) and throws if every attempt fails. The API's failures are random rather than load-related, so backoff isn't strictly needed here, but it's the safe default to avoid hammering a struggling server.
- Adopted TanStack React Query in the dashboard for request state (loading/error/success, caching, deduplication) instead of hand-rolled `useState`/`useEffect`. Its built-in retries are disabled (`retry: false`) because `apiFetch` in core already owns retry/backoff, and that logic needs to stay in core so the CLI gets it too.
- Each user row runs its own React Query for that user's logins (`['logins', userId]`), so rows load and fail independently and the cache can be reused by the side panel later. Request volume and rate limiting are deferred until this works end to end.
- Set `staleTime: Infinity` for all queries: the data doesn't change within a session, and this prevents React Query from refetching all 1,000 login queries on window focus.
- `fetchUserLogins` parses the raw API response into core's exported `UserLogins` type: `login_time` becomes a `Date`, `logins` is sorted newest first, and an explicit nullable `last_login` is provided. The raw response shape (`ApiUserLogins`) stays private to core, so consumers only see parsed data. A plain type was chosen over a `Login` class with formatting getters.
- Failures that survive all retries get their own visible states, separate from empty data: a page-level alert banner if the user list can't load, a compact "Failed to load" in a row's login cells if that user's logins can't load, and "Never" for a user who loaded successfully with no logins.
- The details panel is always visible as a fixed-width right column, with a "Select a user" empty state, rather than appearing only on selection. Users are selected with a real `<button>` in the name cell rather than an `onClick` on the `<tr>`, so selection works by keyboard and is announced as interactive.
- "Hasn't logged in for a month" means before the same date one calendar month ago (`Date#setMonth`), not a fixed 30 days. It's computed in the dashboard row component and shown as an orange dot with an accessible label.
- Added a deliberately thin CLI (`sitewire-interview-cli`) to show that core's data logic works outside React, not to match the dashboard's features. By default it prints the first 15 users as a plain table plus a "… N more" count (no TUI), and it only fetches logins for the rows it prints.
- The CLI silences core's `console.debug` attempt tracing by overriding `console.debug` globally unless `--verbose` is passed. This is a knowing hack, commented as such in the code, chosen over adding a logging option to core because it keeps core unchanged and the CLI owns its whole process.
- `apiFetch` caps concurrent network requests at 50 with a module-level counter and FIFO waiting queue (a semaphore). The slot is held per attempt (only around the `fetch` itself), not for the whole retry sequence, so requests in backoff don't hold slots and retries rejoin the back of the queue. Living in core, the limit applies to the dashboard and the CLI alike.
- CLI `--json` output keeps "failed to load" separate from "never logged in": each user gets `last_login` (or `null`) plus an explicit `logins_failed` flag. With `--verbose`, trace logs go to stderr so stdout stays valid JSON.
- Each request attempt has a 10s timeout (`AbortSignal.timeout`), started only once the request has a concurrency slot so queue time doesn't count. Timeouts and network errors are retried exactly like a 500, and the final error reports the attempt count (from `BACKOFF_MS.length`) plus the last failure reason.
